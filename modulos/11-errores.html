Errores y depuración

Tarde o temprano algo falla: una API no responde, cambia un campo o caduca una credencial. La diferencia entre un workflow de juguete y uno de verdad es qué pasa entonces. En este módulo aprendes a encontrar y leer los errores, a reintentar lo que falla de forma pasajera, a desviar los errores por otra rama y a recibir un aviso cuando un workflow se rompe mientras tú no miras.

Basado en la documentación y el código de n8n 2.x (estable 2.49.8 a finales de noviembre de 2026): ajustes de nodo del motor n8n-core, Error Trigger 1, Stop and Error 1 y HTTP Request 4.5. La práctica usa httpbin.org para provocar errores a propósito, sin cuentas ni claves.

¿Qué puede fallar?

No todos los errores son iguales, y no todos se arreglan igual. Antes de tocar nada, pregúntate de qué tipo es:

TipoEjemplosQué hacer
PasajeroServicio caído un momento (503), demasiadas peticiones (429), red lenta, tiempo agotadoReintentar: Retry On Fail
De datosUn item sin email, una fecha mal escrita, una URL que no existe (404)Separar ese item por otra rama (On Error) o filtrarlo antes
De configuraciónCredencial caducada (401), permiso que falta (403), campo mal escrito en una expresiónArreglar el workflow; reintentar no sirve
De lógicaEl workflow termina «bien» pero hace algo que no debería (0 items, un total que no cuadra)Provocar tú el error con Stop and Error para enterarte

Por defecto, cuando un nodo falla, se para todo el workflow y la ejecución queda marcada como fallida. Es lo más seguro: mejor parar que enviar 500 emails con datos a medias. Pero muchas veces querrás otra cosa, y para eso están los ajustes de este módulo.

Leer un error

Cuando un nodo falla en el editor, se pone en rojo con un triángulo de aviso. Ábrelo: en el panel Output aparece el error en lugar de los datos.

Lo que ves en el panel Output (resumido)
The resource you are requesting could not be found   ← mensaje: qué ha pasado
(debajo, a veces, una descripción con más detalle)

Error details
  From Comprobar web            ← nodo que falló
  HTTP Code     404             ← código HTTP
  Full message  …               ← respuesta completa del servicio
  Request       { "method": "GET", "uri": "https://httpbin.org/status/404", … }
Other info
  Item Index    1               ← qué item lo provocó (empieza en 0)
  Node type · Node version · n8n version · Time
  • MensajeLo primero que tienes que leer. En los errores HTTP, n8n traduce el código a una frase: 401 «Authorization failed», 404 «could not be found», 429 «too many requests», 503 «Service unavailable – … consider setting this node to retry automatically». La tabla completa está en el módulo 8.
  • Item IndexQué item falló (empezando por 0). Si 99 items van bien y uno falla, aquí sabes cuál: búscalo en el panel Input.
  • RequestEn nodos que llaman a una API, la petición exacta que se envió (con las credenciales ocultas). Compárala con la documentación de la API.
  • Copy to ClipboardCopia todos los detalles para pedir ayuda (en el foro de n8n, por ejemplo). Revisa antes que no lleven datos personales.

Un truco que ahorra horas: lee el mensaje en voz alta y traduce cada palabra. «Cannot read properties of undefined (reading 'email')» significa «he intentado leer email dentro de algo que no existe»: el campo de arriba se llama distinto o falta en ese item.

El historial: pestaña Executions

Cada vez que un workflow se ejecuta, n8n guarda una ejecución (execution): qué datos entraron y salieron de cada nodo, cuánto tardó y si falló. Las ves en la pestaña Executions de cada workflow (arriba, junto a Editor) o en Overview → Executions para todos.

  • EstadosSuccess (bien), Error (falló), Running (en marcha), Waiting (en un nodo Wait o esperando un webhook), Canceled (la paraste tú) y Success retry (falló, pero un reintento posterior salió bien).
  • FiltersFiltra por estado, fecha o workflow. Activa Auto refresh para ver las nuevas mientras llegan.
  • Abrir una ejecuciónMuestra el workflow tal como estaba, en solo lectura, con los datos de cada nodo. Haz doble clic en un nodo para ver su Input y su Output de ese momento. El nodo que falló sale en rojo.
  • Retry executionEn una ejecución fallida, vuelve a lanzarla desde el nodo que falló con los mismos datos de entrada: Retry with current version (con tus cambios, para cuando ya lo has arreglado) o Retry with original version (exactamente como estaba, para fallos pasajeros). Útil cuando un servicio estuvo caído un rato.

Las ejecuciones manuales (las que lanzas con Execute workflow) también se guardan, pero lo importante son las de producción: las que lanzan los triggers de un workflow publicado mientras no estás delante. Ahí no ves el lienzo en rojo: o miras Executions, o te avisa un error workflow (más abajo).

Depurar: encontrar dónde y por qué

  1. Localiza el nodo. En la ejecución fallida, el nodo rojo es donde se detuvo. Pero el culpable puede estar antes: mira su Input. ¿Llegan los datos que esperabas?
  2. Reproduce el fallo en el editor. Con Debug in editor (en la ejecución fallida) n8n copia los datos de esa ejecución en tu workflow y los fija (pin) en el primer nodo. Así repites el fallo con los mismos datos, sin esperar al trigger ni llamar otra vez a la API. En ejecuciones correctas el botón se llama Copy to editor.
  3. Prueba nodo a nodo. Con Execute step ejecutas solo hasta ese nodo. Fija (Pin data, tecla P) la salida de los nodos lentos o caros para no repetirlos en cada prueba.
  4. Mira dentro de las expresiones. En el editor de expresiones, la vista previa enseña el resultado del item seleccionado. Si sale undefined o [null], ahí está el problema.
  5. Corrige, ejecuta y quita los pins. Cuando funcione, despinea los datos (Unpin) y prueba con datos reales antes de publicar.

Debug in editor está disponible en todos los planes de n8n Cloud y, en una instalación propia, en la Community Edition registrada (gratis: n8n te ofrece registrarla con tu email y te envía una clave de licencia). Sin registrar, al pulsarlo aparece un aviso para mejorar el plan. Siempre puedes copiar a mano la salida de un nodo de la ejecución y pegarla como datos fijos en el editor.

Para ejecutar un trozo sin borrar nada, desactiva temporalmente un nodo: selecciónalo y pulsa D (Deactivate). Los datos pasan a través de él sin cambios. Y para dejar pistas a quien venga detrás (o a ti), usa Settings → Notes con Display Note in Flow?: la nota aparece bajo el nodo en el lienzo.

Ajustes del nodo para errores

Todos los nodos tienen una pestaña Settings junto a Parameters. Ahí están las cuatro opciones que deciden qué pasa cuando ese nodo falla.

Retry On Fail: reintentar

Si el nodo falla, n8n espera un poco y lo vuelve a ejecutar entero (con todos sus items, no solo el que falló).

  • Max. TriesIntentos en total, contando el primero. Por defecto 3; entre 2 y 5.
  • Wait Between Tries (ms)Espera entre intentos, en milisegundos. Por defecto 1000 (1 segundo); máximo 5000.

Es la solución para los errores pasajeros (503, 429, cortes de red). Para un 404 o un 401 no sirve: el tercer intento falla igual que el primero, solo que más tarde.

Ojo con los nodos que hacen cosas: si un nodo envía 10 emails y falla en el octavo, al reintentar vuelve a enviar los 10. Para estos casos, procesa de uno en uno (con Loop Over Items, módulo 7) o reintenta solo lo seguro, como leer datos.

On Error: qué hacer si falla

OpciónQué pasaCuándo usarla
Stop WorkflowPor defecto. El workflow se para y la ejecución queda como ErrorCuando un fallo debe detenerlo todo
ContinueEl workflow sigue. Los items que fallan salen por la salida normal, mezclados con los buenos, con un campo errorCuando un fallo no importa mucho y lo tratas después con un If
Continue (using error output)Aparece una segunda salida, error. Los items buenos salen por Success y los que fallan por Error, con sus datos de entrada más el errorLa más útil: tratas cada caso por su rama

Con Continue (using error output), un item que falla en el HTTP Request sale por la rama de error con sus campos de entrada y dos campos nuevos:

Item en la salida «Error» del HTTP Request 4.5 (resumido)
{
  "nombre": "Tienda",                           ← datos de entrada
  "url": "https://httpbin.org/status/404",
  "error": { … },                                ← el error original, completo
  "details": {                                   ← resumen fácil de usar
    "message": "The resource you are requesting could not be found",
    "httpCode": "404",
    "body": ""
  }
}

En el nodo siguiente usas {{ $json.details.message }} y {{ $json.details.httpCode }}. Con Continue a secas, el item de error lleva solo error y details: los datos de entrada no vienen, y tendrías que recuperarlos con $('Nodo anterior').item.

Con cualquiera de las dos opciones Continue, el nodo ya no «falla»: la ejecución termina como Success aunque la mitad de los items tengan error. Eso significa que no se dispara el error workflow. Si quieres enterarte, añade un Stop and Error en la rama de error.

Always Output Data y Execute Once

  • Always Output DataSi el nodo no saca ningún item (un Filter que lo descarta todo, una búsqueda sin resultados), saca uno vacío {} para que el workflow no se pare ahí. Útil para avisar de «hoy no hay nada». Cuidado: el item vacío llega a los nodos siguientes y puede provocar errores raros si no lo esperan.
  • Execute OnceEl nodo se ejecuta una sola vez, con el primer item. Evita, por ejemplo, enviar el mismo aviso 20 veces porque llegan 20 items.

Fallar a propósito: Stop and Error

A veces nada «falla», pero el resultado está mal: la API devolvió 0 pedidos un lunes, o un total es negativo. El nodo Stop and Error para el workflow con el error que tú escribas, y la ejecución queda como fallida (con todo lo que eso implica: aparece en rojo en Executions y dispara el error workflow).

  • Error TypeError Message (un texto, admite expresiones) o Error Object (un JSON con message, description y lo que quieras).

Lo normal es ponerlo detrás de un If o en la rama de error: «si no hay pedidos → Stop and Error: No ha llegado ningún pedido hoy».

Que te avisen: el error workflow

Un error workflow es un workflow normal que empieza por el trigger Error Trigger. Lo asignas a otros workflows y, cuando una ejecución de producción de alguno de ellos falla, n8n lo lanza con los datos del fallo. Un mismo error workflow sirve para todos tus workflows.

Cómo se monta

  1. Crea un workflow (por ejemplo, «Avisos de error») y añade el trigger Error Trigger (búscalo como Error).
  2. Detrás, lo que quieras: un mensaje por Telegram o un email (módulo 8), una fila en una hoja de cálculo…
  3. Publícalo. En n8n 2.x se ejecuta la versión publicada del error workflow; si no está publicado, no se lanza (y en los logs de n8n aparece Workflow … is not active and cannot be executed).
  4. En el workflow que quieres vigilar, abre el menú ⋯ → Settings y elige tu workflow en Error Workflow (to notify when this one errors). Guarda.

El Error Trigger recibe un item como este:

Salida del Error Trigger
[
  {
    "execution": {
      "id": "1234",
      "url": "http://localhost:5678/workflow/aBc123/executions/1234",
      "error": { "message": "Hay webs con errores: Tienda (404)", "stack": "…" },
      "lastNodeExecuted": "Avisar del fallo",
      "mode": "trigger"
    },
    "workflow": { "id": "aBc123", "name": "Comprobar webs" }
  }
]
  • execution.urlEnlace directo a la ejecución fallida. Ponlo en el aviso: con un clic ves qué pasó.
  • execution.retryOfSolo aparece si la ejecución fallida era un reintento de otra.
  • triggerSi lo que falla es el propio trigger del workflow (por ejemplo, un trigger de Gmail con la credencial caducada), no hay ejecución: llega un objeto trigger con el error en lugar de execution.

El error workflow no se lanza en las ejecuciones manuales (las de Execute workflow): solo en producción. Para probarlo, ejecuta el error workflow a mano: el Error Trigger saca unos datos de ejemplo (Example Error Message, Example Workflow) con la misma forma que los reales.

Si un workflow no tiene error workflow asignado pero contiene él mismo un Error Trigger, n8n lo usa para sus propios fallos. Es una forma de llevar el aviso dentro, aunque lo habitual es un único error workflow para todos.

Ajustes del workflow

En el menú ⋯ → Settings de cada workflow, además del error workflow, tienes:

AjustePor defectoPara qué
Save failed production executionsGuardarGuardar las ejecuciones de producción que fallan. Déjalo siempre activado
Save successful production executionsGuardarDesactívalo en workflows que se ejecutan muy a menudo para no llenar la base de datos
Save manual executionsGuardarGuardar las ejecuciones que lanzas desde el editor
Save execution progressNo guardarGuardar los datos tras cada nodo: si n8n se cae a mitad, puedes ver hasta dónde llegó (más lento)
Timeout WorkflowDesactivadoCancelar la ejecución si tarda más de Timeout After (evita workflows colgados)

Las ejecuciones no se guardan para siempre: n8n borra las de más de 14 días (336 horas) o, si hay muchas, se queda con las últimas 10 000. Puedes cambiarlo con variables de entorno en el compose.yml del módulo 2:

compose.yml · environment (opcional)
      - EXECUTIONS_DATA_MAX_AGE=720          # horas que se guardan (30 días)
      - EXECUTIONS_DATA_PRUNE_MAX_COUNT=20000 # máximo de ejecuciones guardadas
      - EXECUTIONS_DATA_SAVE_ON_SUCCESS=none  # no guardar las correctas (todas)
      - EXECUTIONS_TIMEOUT=300               # tiempo máximo por defecto, en segundos

Los logs del servidor

Algunos problemas no aparecen en ninguna ejecución: n8n no arranca, un error workflow no se lanza, un webhook no llega. Para esos, mira los mensajes del propio n8n con Docker (módulo 2):

Terminal
docker compose logs -f n8n          # mensajes en directo (Ctrl+C para salir)
docker compose logs --tail 100 n8n  # las últimas 100 líneas

Para ver más detalle mientras investigas, añade N8N_LOG_LEVEL=debug a las variables de entorno del compose.yml y reinicia con docker compose up -d. Los niveles son error, warn, info (por defecto) y debug. Vuelve a info cuando termines: debug escribe muchísimo.

Práctica: vigilante de webs

Vas a construir un workflow que comprueba varias webs cada minuto, separa las que fallan, falla a propósito si alguna está mal y, entonces, otro workflow prepara un aviso. Usarás httpbin.org/status/…, que responde con el código que le pidas.

Workflow «Comprobar webs»

Workflow «Avisos de error»

Parte A · Provocar y leer un error

  1. Crea el workflow «Comprobar webs» con un Trigger manually llamado Al pulsar Ejecutar.
  2. Webs. Añade un Edit Fields llamado Webs en modo JSON:
    JSON Output de «Webs»
    {
  "webs": [
    { "nombre": "Inicio", "url": "https://httpbin.org/status/200" },
    { "nombre": "Tienda", "url": "https://httpbin.org/status/404" },
    { "nombre": "Blog", "url": "https://httpbin.org/status/500" },
    { "nombre": "Contacto", "url": "https://httpbin.org/status/200" }
  ]
}
  3. Separar webs. Un Split Out con Fields To Split Out = webs: 4 items.
  4. Comprobar web. Un HTTP Request con Method GET y URL = {{ $json.url }}. Ejecuta el workflow.
  5. Lee el error. El nodo se pone en rojo. Ábrelo: The resource you are requesting could not be found, HTTP Code 404 y Item Index 1 (la Tienda, el segundo item). Fíjate en que no hay datos de salida: con Stop Workflow se pierde también lo que iba bien.
  6. Mira el historial. Abre la pestaña Executions: la ejecución aparece como Error. Ábrela y haz doble clic en Comprobar web para ver el mismo error. Vuelve a Editor.

Parte B · Reintentar (y ver cuándo no sirve)

  1. En Comprobar web → Settings, activa Retry On Fail (deja Max. Tries 3 y Wait Between Tries 1000).
  2. Ejecuta otra vez. Tarda unos 2 segundos más y falla igual: un 404 no se arregla esperando. Retry On Fail es para fallos pasajeros (en el simulador, prueba la «API inestable»).
  3. Deja Retry On Fail activado: si un día httpbin tarda o se cae un momento, los reintentos lo cubrirán.

Parte C · Separar los errores por otra rama

  1. En Settings, cambia On Error a Continue (using error output). El nodo pasa a tener dos salidas: Success y Error.
  2. Web correcta. En la salida Success, un Edit Fields llamado Web correcta con nombre = {{ $('Separar webs').item.json.nombre }} y estado = OK. (httpbin responde sin contenido, por eso el nombre se recupera de un nodo anterior.)
  3. Web con error. En la salida Error, un Edit Fields llamado Web con error con cuatro campos: nombre = {{ $json.nombre }}, url = {{ $json.url }}, codigo = {{ $json.details.httpCode }} y mensaje = {{ $json.details.message }}.
  4. Ejecuta. Ahora el workflow termina bien: 2 items en Web correcta (Inicio y Contacto) y 2 en Web con error (Tienda con 404 y Blog con 500). Abre la salida de error del HTTP Request y busca details.
  5. Prueba un momento la opción Continue a secas: los 4 items salen juntos por una única salida y los que fallan solo llevan error y details (sin nombre). Vuelve a Continue (using error output).

Parte D · Fallar a propósito

  1. Tal como está, la ejecución termina en Success aunque haya webs caídas, así que nadie se enteraría. Detrás de Web con error, añade un Stop and Error llamado Avisar del fallo.
  2. En Error Message, en modo Expression:
    Error Message de «Avisar del fallo»
    Hay webs con errores: {{ $('Web con error').all().map(i => i.json.nombre + ' (' + i.json.codigo + ')').join(', ') }}
  3. Ejecuta. La ejecución falla con el mensaje Hay webs con errores: Tienda (404), Blog (500). Ese fallo «controlado» es el que va a disparar el aviso.

Parte E · El workflow de avisos

  1. Crea otro workflow llamado Avisos de error. Como trigger, busca Error Trigger.
  2. Ejecútalo a mano: sale un item de ejemplo (Example Error Message, Example Workflow). Te sirve para preparar el resto sin esperar a un fallo real.
  3. Añade un Edit Fields llamado Preparar aviso con estos campos:
    NameValue
    workflow{{ $json.workflow.name }}
    nodo{{ $json.execution.lastNodeExecuted }}
    error{{ $json.execution.error.message }}
    enlace{{ $json.execution.url }}
    modo{{ $json.execution.mode }}
    aviso⚠ Ha fallado «{{ $json.workflow.name }}» en el nodo «{{ $json.execution.lastNodeExecuted }}»: {{ $json.execution.error.message }}
  4. (Opcional) Si hiciste el módulo 8, añade detrás un Telegram o un Gmail que envíe {{ $json.aviso }} y {{ $json.enlace }}.
  5. Publica «Avisos de error» (Shift + P). Sin publicar no se lanzará.

Parte F · Conectarlos y probar en producción

  1. Vuelve a «Comprobar webs». Abre ⋯ → Settings, elige Avisos de error en Error Workflow (to notify when this one errors) y guarda.
  2. Ejecuta a mano: falla, pero «Avisos de error» no se lanza (mira su pestaña Executions). Es lo esperado: las ejecuciones manuales no disparan el error workflow.
  3. Añade un Schedule Trigger llamado Cada minuto (Trigger Interval = Minutes, Minutes Between Triggers = 1) y conéctalo también a Webs. Publica el workflow.
  4. Espera un par de minutos. En Executions de «Comprobar webs» verás ejecuciones en Error; en las de «Avisos de error», ejecuciones correctas. Abre una: Preparar aviso tiene el mensaje y el enlace a la ejecución fallida (con modo = trigger). Pulsa el enlace.
  5. Despublica «Comprobar webs» para que no siga ejecutándose cada minuto.

Para practicar la depuración, abre una de las ejecuciones fallidas y prueba Retry execution y, si tu instalación está registrada, Debug in editor. Después cambia la URL del Blog a https://httpbin.org/status/200 en Webs y reintenta con Retry with current version.

Problemas frecuentes

El error workflow no se lanza

Revisa, por orden: 1) ¿era una ejecución manual? Esas no lo disparan. 2) ¿Está publicado el error workflow? 3) ¿Empieza por un Error Trigger? 4) ¿Está elegido en Settings → Error Workflow del workflow que falla? 5) ¿Falló de verdad? Con On Error en Continue la ejecución termina en Success. Si todo está bien, mira docker compose logs n8n.

Retry On Fail no reintenta

Con On Error en Continue o Continue (using error output), el nodo no falla: n8n solo lo reintenta si el primer item sale con error. Si necesitas reintentar cada item, déjalo en Stop Workflow con Retry On Fail, o reintenta la rama de error con un bucle.

$json.details sale vacío

El campo details lo añade el HTTP Request desde su versión 4.5. En nodos más antiguos, o en otros nodos, el error está solo en $json.error (a veces un texto, a veces un objeto con message). Mira la salida de error en vista JSON para ver qué trae.

En la rama de error falta el nombre o los datos de entrada

Estás usando Continue a secas, que no copia los campos de entrada. Usa Continue (using error output) o recupera los datos con {{ $('Separar webs').item.json.nombre }}.

«Upgrade to access Debug In Editor»

Tu instalación no está registrada. La Community Edition registrada es gratuita y desbloquea esta función. Mientras tanto, copia los datos de la ejecución y fíjalos a mano con Pin data.

Una ejecución de hace un mes ya no aparece

n8n borra las ejecuciones de más de 14 días (o las que pasan de 10 000). Cámbialo con EXECUTIONS_DATA_MAX_AGE y EXECUTIONS_DATA_PRUNE_MAX_COUNT. Comprueba también que el workflow guarda las ejecuciones correctas en sus Settings.

Una ejecución se queda en Running para siempre

Algún nodo espera algo que no llega (una API que no responde, un Wait muy largo). Párala desde Executions y pon un límite en Settings → Timeout Workflow. En el HTTP Request, ajusta Options → Timeout.
